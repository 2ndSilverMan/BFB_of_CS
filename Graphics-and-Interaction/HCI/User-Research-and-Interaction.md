# 사용자 연구와 상호작용 설계 (User Research and Interaction)

## 개념 (Concept)

사용자 연구는 누가 어떤 상황에서 무엇을 하려는지, 무엇이 방해하는지에 대한 근거를 수집하는 활동이다. 상호작용 설계는 그 근거를 바탕으로 사용자의 행동과 시스템의 응답을 구성한다. 요구사항을 그대로 화면으로 옮기거나 인터뷰 발언을 즉시 기능 목록으로 바꾸는 것과 다르다. 이 문서는 연구 질문·과업 분석·프로토타입과 평가 연결까지 다룬다.

## 직관 (Intuition)

“검색창을 더 크게 해 달라”는 말은 검색창 크기 문제일 수도 있지만, 원하는 항목을 분류로 찾지 못한다는 신호일 수도 있다. 요청된 해결책, 사용자가 겪은 사건, 연구자의 해석을 분리하면 잘못된 기능을 빠르게 만드는 일을 줄일 수 있다.

## 이론 (Theory)

연구 질문은 제품 판단과 연결한다. “앱이 마음에 드는가”보다 “예약을 바꾸는 사람이 취소와 변경을 구별하는가”가 관찰·설계로 이어지기 쉽다. 방법은 질문에 맞춘다. 인터뷰는 경험·맥락을 탐색하고, 관찰은 실제 행동과 환경을 드러내며, 프로토타입 평가는 특정 상호작용을 시험한다. 선호도 응답만으로 행동 성공을 추정하지 않는다.

[GOV.UK의 연구 계획 지침](https://www.gov.uk/service-manual/user-research/plan-user-research-for-your-service)은 서비스 개발의 의사결정과 연구 질문·계획을 연결하는 자료다. 아래 예약 사례와 산출물은 독립적으로 만든 교육용 설계이며 실제 조사 결과가 아니다.

상호작용은 목표 → 행동 선택 → 입력 → 시스템 상태 변화 → 피드백 → 다음 행동으로 분석한다. 사용자가 현재 상태·가능 행동·결과·복구 방법을 알 수 있어야 한다. 초기 프로토타입은 자세한 구현보다 검증할 불확실성에 맞는 충실도가 중요하다.

## 구현 (Implementation)

가상 서비스의 과업은 “다음 주 화요일 예약을 목요일 같은 시간으로 변경”이다. 변경과 취소가 혼동될 수 있다는 가설을 세운다.

| 구분 | 교육용 기록 |
|---|---|
| 의사결정 | 상세 화면에 별도 변경 행동을 둘 것인가 |
| 연구 질문 | 사용자가 기존 예약을 잃지 않고 날짜를 바꿀 수 있는가 |
| 참여 조건 | 예약 경험이 다른 사람, 모바일 사용·접근성 요구 고려 |
| 관찰할 행동 | 변경 진입, 날짜 선택, 확인 전 기존/새 정보 비교, 오류 복구 |
| 수집하지 않을 것 | 실제 예약 번호·건강 정보·실명 등 과업에 불필요한 정보 |
| 판단 기준 | 잘못된 취소·복구 실패의 발생과 원인; 단순 만족도만 사용하지 않음 |

프로토타입은 세 상태로 설계한다.

1. 예약 상세: 현재 예약과 “날짜 변경” 행동.
2. 날짜 선택: 기존 예약은 유지된다는 설명, 가능한 날짜, 취소 가능한 변경 절차.
3. 변경 확인: 이전/이후 날짜를 나란히 제시하고 최종 확정.

입력 오류 시 전체 폼을 지우지 않고 해당 날짜를 수정하도록 한다. 서버 응답이 늦으면 진행 상태를 알리고 중복 확정을 방지한다. 이 설계가 실제로 효과적인지는 후속 평가가 필요하다.

노트는 **관찰** “참여자가 취소 버튼을 눌렀다”, **해석** “변경과 취소를 같은 절차로 이해했을 수 있다”, **후속 질문** “다른 화면에서도 같은가”를 나눠 기록한다. 가상의 노트를 실제 참여자 인용처럼 공개하지 않는다.

## 복잡도 (Complexity)

비용은 모집·준비·진행·분석·설계 반복에 걸친다. 소규모 질적 연구는 문제의 기전을 찾는 데 유용하지만 모집단 발생률의 정밀 추정을 보장하지 않는다. 모집 채널이 숙련 사용자에 치우치면 신규 사용자의 어려움을 놓친다. 실제 사람 대상 연구에는 동의·접근성·철회·보관 기간과 소속 기관의 적용 절차를 사전에 확인한다.

## 응용 (Applications)

업무 시스템, 교육 도구, 공공 서비스, 개발 도구의 과업과 오류 복구 설계에 적용한다. “개발자는 모두 키보드를 잘 쓴다” 같은 추정도 실제 대상과 환경에 따라 확인해야 한다.

## 흔한 오해 (Common Misunderstandings)

- 사용자 의견이 곧 요구사항이다: 발언의 맥락과 실제 과업을 확인한다.
- 연구는 디자인이 끝난 뒤 한다: 무엇을 만들지 결정하는 초기에 필요할 수 있다.
- persona를 만들면 근거가 생긴다: 자료 없는 persona는 가설을 정리한 도구일 뿐이다.

## TMI

- 프로토타입의 시각적 완성도가 높으면 참여자가 변경 가능성이 적다고 느껴 비판을 줄일 수 있다.
- 보이지 않는 백오피스 절차도 사용자 경험을 결정한다. 화면 밖의 인계·알림을 과업에 포함한다.

## 연습 / 확인 문제 (Exercises)

1. “사용자는 새 디자인을 좋아한다”를 검증 가능한 질문으로 바꿔라. **예시 답:** 도움 없이 예약 변경을 완료하고 바뀐 날짜를 정확히 설명할 수 있는가.
2. 예약 수정 중 서버가 실패했다면 어떤 상태를 보여야 하나? **판단 기준:** 기존 예약 유지 여부, 실패 사실, 재시도·복구 행동이 구별되어야 한다.
3. 동료 개발자 두 명의 반응만으로 전체 사용자 요구를 확정해도 되는가? **답:** 안 된다. 표본과 사용 환경의 범위를 제한해서 보고한다.
