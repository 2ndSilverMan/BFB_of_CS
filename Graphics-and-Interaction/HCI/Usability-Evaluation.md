## 개념 (Concept)

사용성 평가는 특정 사용자가 특정 환경에서 과업을 얼마나 효과적·효율적·만족스럽게 수행하는지 근거를 모으는 활동이다. 소프트웨어 테스트가 명세대로 동작하는지 보는 것과 달리, 사용자가 목표를 달성하는 과정의 문제를 다룬다. 이 문서는 진행형 과업 평가의 설계·기록·해석을 다룬다.

## 직관 (Intuition)

버튼을 누르면 예약이 정확히 바뀐다는 자동 테스트가 통과해도 사용자가 그 버튼을 찾지 못할 수 있다. 반대로 화면을 빨리 통과했다고 과업이 성공한 것도 아니다. 잘못된 날짜로 예약하고 완료했다고 생각했다면 빠른 실패다.

## 이론 (Theory)

평가 전 과업·시작 상태·성공 조건·도움 규칙·중단 조건을 정한다. 과업은 “상단 수정 버튼을 누르세요”가 아니라 달성할 목표로 제시한다. 진행자는 답을 유도하지 않고 관찰하며, 도움을 줬다면 그 시점과 내용을 기록한다. [GOV.UK 진행형 사용성 평가 지침](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)은 준비·진행·관찰을 연결하는 기준이다.

완료율의 분모는 시도 수, 시간은 시작·끝 정의가 필요하다. 실패·중단을 성공 시간 평균에서 제외했다면 반드시 별도로 보고한다. 동일 인물이 여러 과업을 수행하면 기록들이 독립적이지 않을 수 있다. 버전 A/B를 같은 사람이 순서대로 경험하면 학습·피로 효과가 생긴다. 순서를 나누는 counterbalancing은 편향을 줄이는 설계 중 하나지만 모든 순서 효과를 없애지는 않는다.

## 구현 (Implementation)

아래는 **가상 참여자 여섯 명**의 예약 변경 결과다. timeout은 120초, 성공은 “도움 없이 올바른 새 날짜로 확정하고 그 날짜를 설명”으로 정했다.

| ID | 결과 | 초 | 관찰 |
|---|---|---:|---|
| P1 | 성공 | 45 | 직접 완료 |
| P2 | 성공 | 50 | 확인 화면 재확인 |
| P3 | 성공 | 80 | 날짜 선택에서 되돌아감 |
| P4 | 성공 | 90 | 변경 상태 안내를 다시 읽음 |
| P5 | 실패 | 120 | timeout |
| P6 | 실패 | 30 | 잘못된 날짜를 확정 |

```python
from statistics import mean, median
rows = [(True, 45), (True, 50), (True, 80),
        (True, 90), (False, 120), (False, 30)]
success_times = [seconds for success, seconds in rows if success]
assert sum(ok for ok, _ in rows) == 4
assert mean(success_times) == 66.25
assert median(success_times) == 65
assert len(rows) == 6
```

보고 예시는 “이 가상 세션에서 4/6 성공, 성공자 시간 평균 66.25초·중앙값 65초, timeout 1건·잘못된 확정 1건”이다. 모집단 성공률이 정확히 66.7%라고 결론 내리지 않는다. 작은 편의표본이고 실제 모집·진행도 없었다.

문제 우선순위는 관측 빈도 하나로 정하지 않는다. 잘못된 날짜 확정은 한 건이어도 결과의 심각성·발견 가능성·복구 비용이 크다. “사용자 부주의”로 끝내지 말고 확인 화면의 이전/이후 정보와 되돌리기 설계를 후속 평가 대상으로 잡는다.

## 복잡도 (Complexity)

N명과 K개 과업의 기록량은 대략 NK에 비례하지만 분석은 맥락·원인 비교 때문에 단순 자동 집계로 끝나지 않는다. 생각을 소리 내게 하는 방식이 자연스러운 과업 속도를 바꿀 수 있다. 원격 환경에서는 네트워크·화면 공유·보조 기술 조건도 기록한다.

## 응용 (Applications)

초기 프로토타입 개선, 오류 복구 검증, 기존 서비스 변경의 위험 확인에 적용한다. 전문가 점검·접근성 검사·사용자 과업 평가는 서로 보완하지만 어느 하나가 나머지를 자동 대체하지 않는다.

## 흔한 오해 (Common Misunderstandings)

- 여섯 명이면 모든 문제를 찾는다: 보편적으로 보장되는 수는 아니다.
- 평균 시간이 줄었으면 개선이다: 성공률·오류 심각성·과업 구성을 함께 본다.
- 참여자가 좋다고 말했으면 성공이다: 선호·완료·효율을 분리한다.

## TMI

- 도움을 준 뒤 완료한 결과는 독립 성공과 구별해야 설계의 도움 의존성을 볼 수 있다.
- 실패 시간을 성공 시간에 임의로 섞으면 “빠른 실패”가 효율 개선처럼 나타날 수 있다.

## 연습 / 확인 문제 (Exercises)

1. P6를 성공으로 잘못 기록하면 어떤 결론이 바뀌나? **답:** 성공률이 5/6로 부풀고 성공 시간 평균도 낮아진다.
2. A를 먼저, B를 나중에 모두 시험했는데 B가 빨랐다면? **판단 기준:** 설계 효과 외에 학습·과업 난도·피로·진행자 도움을 검토한다.
3. P5의 120초는 정확한 완료 시간인가? **답:** 아니다. 시간 제한까지 미완료라는 검열된 관측이다.
