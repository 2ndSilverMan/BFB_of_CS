## 개념 (Concept)

접근성은 다양한 감각·운동·인지 조건과 보조 기술을 사용하는 사람이 정보를 이해하고 기능을 사용할 수 있게 만드는 속성이다. 특정 장애 하나를 위한 부가 기능이나 색 대비 점검만을 뜻하지 않는다. 여기서는 웹 폼의 의미 구조·키보드 조작·피드백을 다루며, 전체 WCAG 적합성 판정을 수행하지 않는다.

## 직관 (Intuition)

마우스로 클릭 가능한 회색 사각형이라도 키보드로 도달할 수 없고 스크린 리더가 이름을 읽지 못하면 일부 사용자는 기능의 존재조차 알 수 없다. 시각적 모양, 프로그램이 전달하는 의미, 실제 조작 가능성을 따로 확인해야 한다.

## 이론 (Theory)

[WCAG 2.2](https://www.w3.org/TR/WCAG22/)는 지각·조작·이해·견고성의 관점과 개별 성공 기준을 제공한다. 이 문서는 키보드 조작, 레이블, 오류 안내, 색 외의 단서, 초점 표시를 확인할 출발점으로 사용한다. 일부 기준을 만족했다고 사이트 전체의 특정 적합성 수준을 선언할 수는 없다.

HTML의 기본 button·input·label은 의미와 기본 상호작용을 제공한다. 임의 div에 click handler만 넣는다면 역할·이름·키보드·초점 동작을 직접 구현해야 한다. ARIA 속성은 동작 구현을 대신하지 않는다. 숨긴 요소에 초점을 남기거나 시각 순서와 키보드 순서가 크게 어긋나면 과업 수행이 어려워진다.

## 구현 (Implementation)

아래는 독립적으로 작성한 작은 정적 폼이다. 브라우저의 기본 숫자 유효성 검사와 의미 구조를 사용한다. 서버 저장·성공 알림은 구현하지 않았다.

```html
<!doctype html>
<html lang="ko">
<meta charset="utf-8">
<title>수량 입력 연습</title>
<style>
  :focus-visible { outline: 3px solid #111; outline-offset: 3px; }
</style>
<main>
  <h1>신청 수량</h1>
  <form>
    <label for="quantity">수량</label>
    <p id="quantity-help">1개부터 5개까지 입력하세요. 필수 항목입니다.</p>
    <input id="quantity" name="quantity" type="number"
           min="1" max="5" required aria-describedby="quantity-help">
    <button type="submit">입력값 확인</button>
  </form>
</main>
</html>
```

검사 계획은 다음과 같다. 이것은 실행 결과가 아니라 확인할 절차다.

| 검사 | 행동 | 기대 관찰 |
|---|---|---|
| 키보드 | Tab/Shift+Tab으로 이동 | 입력과 버튼에 접근하고 초점 위치를 볼 수 있음 |
| 이름·설명 | 스크린 리더로 입력에 접근 | 수량 레이블과 도움말의 관계를 파악할 수 있음 |
| 경계값 | 빈 값, 0, 6, 1, 5로 제출 시도 | 앞의 세 경우 제약 위반, 뒤의 두 경우 통과 |
| 확대 | 글자를 크게 하고 좁은 화면 사용 | 내용과 조작 수단이 겹치거나 사라지지 않음 |

맞춤 오류를 구현한다면 색만 바꾸지 않고 무엇을 어떻게 수정할지 텍스트로 안내하고 입력과 연결한다. 비동기 성공·실패 메시지도 적절히 전달되도록 설계해야 한다. 실제 알림 방식은 브라우저·보조 기술 조합에서 확인한다. 클라이언트 검증이 있어도 서버에서는 입력을 다시 검증해야 한다.

## 복잡도 (Complexity)

자동 도구는 일부 구조·대비 문제를 찾을 수 있지만 과업의 의미, 유용한 대체 텍스트, 조작 흐름 전체를 판정하지 못한다. 테스트 범위는 요소 수뿐 아니라 상태·입력 방식·보조 기술 조합에 따라 늘어난다. 사용자 테스트도 모든 적합성 기준 검사를 대신하지 않는다.

## 응용 (Applications)

예약·결제·학습·행정 폼, 개발 도구, 문서 탐색에 적용한다. 영상에는 자막, 그래프에는 데이터 표·텍스트 설명처럼 매체에 맞는 대안이 필요하다.

## 흔한 오해 (Common Misunderstandings)

- ARIA를 많이 넣을수록 좋다: 잘못된 이름·역할은 오히려 의미를 훼손한다.
- 스크린 리더만 되면 접근성이 끝난다: 키보드·확대·인지·운동 조건도 있다.
- 자동 점수 100이면 적합성 보장이다: 자동 검사 범위를 넘어선 확인이 필요하다.

## TMI

- button 요소도 submit, button, reset의 역할을 구분해야 예상하지 않은 제출을 막을 수 있다.
- 초점 표시를 없애는 스타일 변경은 외형 개선처럼 보여도 조작 정보를 제거할 수 있다.

## 연습 / 확인 문제 (Exercises)

1. 빨간 테두리만으로 오류를 표시하면 무엇이 빠졌나? **답:** 색을 구분하지 못하거나 시각 정보에 접근하지 못하는 사람에게 오류와 수정 방법이 전달되지 않을 수 있다.
2. 클릭 가능한 div를 native button으로 바꾸는 이점은? **답:** 기본 역할·키보드 동작·초점 동작의 상당 부분을 재사용한다. 전체 접근성이 자동 보장되는 것은 아니다.
3. 위 폼이 WCAG 2.2 AA를 만족한다고 선언할 수 있는가? **답:** 이 예제·정적 점검만으로는 불가. 전체 범위와 모든 해당 기준, 실제 동작을 확인하지 않았다.
