## 개념 (Concept)

연구 운영은 질문·사람·시간·장비·데이터·책임을 연결해 연구를 수행 가능한 상태로 만드는 일이다. 연구 결과를 미리 보장하는 프로젝트 관리가 아니라 불확실성을 줄이고 실패에서도 근거를 남기는 과정이다. 이 문서는 소규모 팀의 계획·역할·기여·리스크·인계를 다룬다. 연구비 신청의 법적·회계적 절차는 기관별로 별도 확인한다.

## 직관 (Intuition)

“모델을 만들고 논문을 쓴다”는 계획에는 입력 자료가 언제 준비되는지, 기준선이 실패하면 어떻게 하는지, 누가 결과를 재실행하는지가 없다. 발표 날짜만 정하는 것보다 중간의 판단 가능한 산출물과 중단·축소 조건을 정하는 편이 불확실성을 관리하기 쉽다.

## 이론 (Theory)

질문 → 검증 방법 → 산출물 → 작업 의존성 → 자원·책임을 거꾸로 연결한다. 마일스톤은 “코드 50%”보다 “기준선이 고정 입력에서 실행되고 결과가 기록됨”처럼 확인 가능한 증거로 정의한다. 새로운 결과가 나오지 않아도 재현 실패·반례·자료 한계를 산출물로 남길 수 있다.

기여 인정은 마지막에 갑자기 결정하기보다 시작 시 기대와 변경 절차를 합의한다. [NISO CRediT](https://credit.niso.org/)는 연구 기여를 역할로 기술하는 참고 체계이며 저자 자격의 자동 판정기는 아니다. 설계·구현·검증·자료 관리·초고·수정 기여를 기록하되 실제 투고 기준과 최종 책임 동의를 따로 확인한다.

책임자는 작업을 직접 수행하는 사람과 항상 같지 않다. 승인·수행·자문·통보를 구분하면 막힌 결정의 주인을 알 수 있다. 개인정보·장비 안전·기밀 자료는 팀 내부 합의만으로 자유롭게 처리하지 않는다.

## 구현 (Implementation)

가상 4주 프로젝트의 질문은 “두 교체 정책을 같은 입력에서 비교할 수 있는가”다. 성능 우승이나 논문 채택은 성공 기준으로 보장하지 않는다.

| 주 | 산출물 | 책임 | 통과/축소 조건 |
|---|---|---|---|
| 1 | 질문·가정·자료 권한·기준선 계획 | A, B 검토 | 자료 권한 불명확하면 공개 합성 입력으로 범위 축소 |
| 2 | 기준선 실행과 기대값 테스트 | B, A 재실행 | 실행 안 되면 새 기법 추가보다 원인 기록 |
| 3 | 비교 실험·원시 결과·분석 | A와 B | 환경 차이가 크면 통제 실험부터 반복 |
| 4 | 주장–근거–한계 보고서와 인계 | 공동 | 새 우수성 미입증이면 결과 범위 축소 |

교육용 계산 자원 예산은 작업 20회×가정 0.5시간=10시간이다. 재실행 여유 50%를 두면 15시간이다. 실제 장비 가격·결제·연구비 규정이 아닌 실행 시간 계획이며, pilot 결과가 2시간이면 원 계획을 40시간 기준으로 재산정해야 한다.

리스크 기록 예시는 다음과 같다.

- 데이터 접근 지연: 담당 A, 첫 주 종료에 확인, 합성 데이터 대안, 실제 데이터 일반화는 포기.
- 실행 환경 차이: 담당 B, 버전·명령 기록, 서로의 환경에서 최소 예제 실행.
- 공동 작업 충돌: 작은 변경과 근거 기록, 원시 결과 덮어쓰기 금지.
- 기여 이견: 역할 기록과 초기 합의를 대조하고 기관의 독립 조정 경로 확인.
- 결과 부정적: 제외하거나 숨기지 않고 질문·조건·실패 증거를 보고.

인계 묶음에는 실행 진입점, 입력 권한·해시, 환경, 원시 결과, 분석 방법, 알려진 실패, 후속 질문과 자료 보관 책임을 포함한다. 비밀번호·접근 토큰은 문서에 넣지 않는다.

## 복잡도 (Complexity)

사람이 N명일 때 모든 쌍의 통신 경로는 N(N−1)/2개이므로 역할과 결정 기록 없이 모든 정보를 구두로 공유하면 비용이 커진다. 그렇다고 문서 양을 무조건 늘리지 않는다. 결과를 재현하고 책임을 찾는 데 필요한 최소 기록을 유지한다. 일정 여유가 있어도 승인·자료 접근의 외부 의존성은 사라지지 않는다.

## 응용 (Applications)

학부 팀 연구, 대학원 프로젝트, 공동 논문, 공개 소프트웨어, 강의 프로젝트를 운영할 때 사용한다. 연구 제안서는 질문·기여 가능성·방법·위험·자원의 논리를 설명해야 하며 결과를 확보하기 전에 성공을 사실처럼 쓰지 않는다.

## 흔한 오해 (Common Misunderstandings)

- 일정대로 끝나면 연구가 성공이다: 질문에 답할 근거가 있어야 한다.
- 커밋 수가 저자 순서를 결정한다: 지적·비코드 기여와 책임을 함께 확인한다.
- 부정적 결과는 산출물이 아니다: 설계·범위·기록이 타당하면 후속 판단에 도움이 된다.

## TMI

- 인계 문서를 프로젝트 마지막에 쓰면 환경의 암묵적 의존성을 놓치기 쉽다.
- 역할은 연구 중 바뀔 수 있으므로 시작 합의뿐 아니라 변경 이유도 기록한다.

## 연습 / 확인 문제 (Exercises)

1. pilot 실행이 예상의 4배 걸린다면 먼저 무엇을 바꿔야 하나? **답:** 총 비용·질문 범위·실험 수·자원 계획을 재산정하고 통계·비교 타당성을 유지할 축소안을 정한다.
2. 결과가 좋게 나온 trial만 보고하면? **답:** 선택적 보고로 결론이 왜곡된다. 제외 규칙과 전체 실행 기록이 필요하다.
3. 팀원이 떠날 때 무엇이 있으면 다른 사람이 이어갈 수 있나? **판단 기준:** 코드뿐 아니라 입력 권한·환경·결정·원시 결과·실패·책임이 연결된다.
